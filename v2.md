# CHIP v2 — UX Improvement Proposals

**Scope:** No new features. Only improvements to the existing user experience within the current surface area — UI, API response shape, parse feedback, error states, and result presentation.

Each proposal below includes the exact files and lines that need to change, and what the change should do.

---

## 1. Parse Preview Shows Nothing Useful

**Problem:** After `/api/parse` returns, the UI dumps a raw JSON blob of the `QuerySpec` into a `<pre>` element. Users see `aoi_name`, `bbox`, `source_text`, `parsed_by`, etc. as a wall of keys. The meaningful signal — *"did the system understand my query correctly?"* — is buried.

**Current code:** [`web/index.html:276`](web/index.html:276)
```js
document.getElementById("spec-display").textContent = JSON.stringify(spec, null, 2);
```

**Proposed change:** Replace the raw JSON dump with a three-line human summary, keeping the raw JSON available behind a disclosure toggle.

```js
function renderSpec(spec) {
  const dateRange = spec.start === spec.end
    ? spec.start
    : `${spec.start} → ${spec.end}`;
  const cloud = spec.max_aoi_cloud < 100
    ? `, max AOI cloud ${spec.max_aoi_cloud}%`
    : "";
  const summary = `${spec.product.replace("_", " ")} · ${spec.aoi_name} · ${dateRange}${cloud}`;
  return `<div style="font-size:14px; color:var(--text); margin-bottom:6px">${summary}</div>`
       + `<details><summary style="color:var(--muted);font-size:11px;cursor:pointer">raw spec</summary>`
       + `<pre class="spec-box" style="margin-top:6px">${JSON.stringify(spec, null, 2)}</pre></details>`;
}
// Then: document.getElementById("spec-display").innerHTML = renderSpec(spec);
```

The spec box `<pre>` becomes the `<details>` body. No API changes needed.

## 2. Status Messages Don't Convey Progress

**Problem:** There are two status strings — `"Parsing query…"` while `/api/parse` runs, then `"Running pipeline… (first run fetches live data, subsequent runs use cache)"` — but they're displayed identically in the same `<div class="spinner">`. The parenthetical about caching is dropped in context the moment the pipeline starts. Once the pipeline is running, there is no feedback that anything is happening.

**Current code:** [`web/index.html:264`](web/index.html:264), [`web/index.html:278`](web/index.html:278)
```js
setStatus('<div class="spinner">Parsing query…</div>');
// ...
setStatus('<div class="spinner">Running pipeline… (first run fetches live data, subsequent runs use cache)</div>');
```

**Proposed change:** Add a stage indicator with elapsed time so the user knows the system is alive during the (potentially 10–30 s) COG fetch.

```js
let _timerHandle = null;
let _timerStart = 0;

function startTimer(label) {
  _timerStart = Date.now();
  clearInterval(_timerHandle);
  _timerHandle = setInterval(() => {
    const s = ((Date.now() - _timerStart) / 1000).toFixed(1);
    setStatus(`<div class="spinner">${label} <span style="color:var(--muted)">(${s}s)</span></div>`);
  }, 200);
}

function stopTimer() {
  clearInterval(_timerHandle);
  _timerHandle = null;
}
```

Replace the two `setStatus` calls:
```js
startTimer("Parsing query…");
// after parse completes:
startTimer("Scoring candidates — fetching SCL bands…");
// in finally:
stopTimer();
```

No backend changes needed.

## 3. The Comparison Table Doesn't Explain the Gap Column

**Problem:** The table header explains what `eo:cloud_cover` is, but the `Gap` column has no legend. Users who glance at the table see `+64.8 pts` in red but may not know whether positive means "more cloudy than stated" or "less cloudy than stated." The colour alone is insufficient — red could mean "bad data" or "bad catalog".

**Current code:** [`web/index.html:183-194`](web/index.html:183)
```html
<th>Gap</th>
```

**Proposed change:** Expand the column header to a short two-word label with a sub-caption directly in the `<th>`:

```html
<th>
  Gap
  <div style="font-size:10px;font-weight:400;color:var(--muted);margin-top:2px">
    red = catalog understates (you got clouds); green = catalog overstates (image was fine)
  </div>
</th>
```

Alternatively, add a one-line key below the table header bar inside `.comparison-table-header`:

```html
<div class="comparison-table-header">

  CHIP measures it over your actual AOI using the SCL band. The gap between these

  (image was usable but would have been filtered out).
</div>
```

No API or backend changes needed.

## 4. The `no_data` Error Case Is a Blank Screen

**Problem:** When `rank_candidates` returns no results, [`app/pipeline.py:138-149`](app/pipeline.py:138) returns a `ChipResult` with `selected=None`, an empty `candidates` list, and a single `fail` check. The frontend's `renderResult` then renders:
- An empty candidates table (no rows)  
- No images (all paths are empty strings)  
- One red QA row: "No valid scenes found"

The overall effect is a mostly-empty page with a small red badge at the bottom. The user has no idea whether the problem is the date range, the AOI, the cloud threshold, or the data source.

**Current code:** [`web/index.html:300-376`](web/index.html:300)

**Proposed change:** In `renderResult`, check for the zero-candidate case and render a prominent inline error banner above the (empty) table, with the fail-check message promoted to it:

```js
function renderResult(result) {
  const failChecks = (result.checks || []).filter(c => c.status === "fail");
  const isEmpty = !result.candidates || result.candidates.length === 0;

  if (isEmpty && failChecks.length > 0) {
    setStatus(`<div class="error-box" style="margin-top:16px">
      <strong>No results.</strong> ${failChecks[0].message}
      <div style="margin-top:8px;color:var(--muted);font-size:11px">
        Try widening the date range, lowering the max-cloud threshold, or choosing a different AOI.
      </div>
    </div>`);
    document.getElementById("results").style.display = "none";
    return;
  }
  // ... existing rendering continues
}
```

The `results` div stays hidden; the error message takes the place of the spinner. No API changes needed.

## 5. Image Panel Shows Duplicate Images for `true_color`

**Problem:** When `product == "true_color"`, [`app/pipeline.py:236`](app/pipeline.py:236) sets `product_path = preview_path` — they point to the same file. The UI then renders the same PNG twice side by side: once labelled "True Colour" and once labelled "TRUE_COLOR". This is confusing and wastes screen space.

**Current code:** [`web/index.html:341-353`](web/index.html:341)
```js
const images = [
  {path: result.preview_png, label: "True Colour"},
  {path: result.product_png, label: result.spec?.product?.toUpperCase() || "Product"},
  {path: result.cloudmask_png, label: "Cloud Mask Overlay"},
];
images.forEach(({path, label}) => {
  if (!path) return;
  // ...
```

**Proposed change:** Deduplicate by path before rendering. If `preview_png` and `product_png` resolve to the same `/outputs/…` URL, skip the second one:

```js
function renderResult(result) {
  // ... existing candidates/stats rendering ...

  const toUrl = path => path ? "/outputs/" + path.split("/outputs/")[1] : null;
  const previewUrl = toUrl(result.preview_png);
  const productUrl = toUrl(result.product_png);
  const cloudUrl   = toUrl(result.cloudmask_png);

  const rawImages = [
    {url: previewUrl,                     label: "True Colour"},
    {url: productUrl !== previewUrl ? productUrl : null,
                                          label: result.spec?.product?.replace("_", " ").toUpperCase() || "Product"},
    {url: cloudUrl,                       label: "Cloud Mask Overlay"},
  ];

  const imagesEl = document.getElementById("images-display");
  imagesEl.innerHTML = "";
  rawImages.forEach(({url, label}) => {
    if (!url) return;
    const card = document.createElement("div");
    card.className = "img-card";
    card.innerHTML = `<img src="${url}" loading="lazy" /><div class="img-label">${label}</div>`;
    imagesEl.appendChild(card);
  });
  // ...
}
```

No API changes. No backend changes.

## 7. The `/api/chip` Endpoint Reconstructs `QuerySpec` by Hand

**Problem:** [`app/main.py:76-86`](app/main.py:76) manually pulls keys out of `req.spec` and constructs a `QuerySpec` by keyword argument. This means any future field added to `QuerySpec` must also be added here — and a mis-named key in the incoming JSON silently falls through to a default. The `source_text` and `parsed_by` fields are already being read with `.get()` defaults that shadow what the parser set.

**Current code:** [`app/main.py:76-86`](app/main.py:76)
```python
spec = QuerySpec(
    aoi_name=d["aoi_name"],
    bbox=d["bbox"],
    start=d["start"],
    end=d["end"],
    product=d.get("product", "true_color"),
    max_aoi_cloud=float(d.get("max_aoi_cloud", 100.0)),
    source_text=d.get("source_text", ""),
    parsed_by=d.get("parsed_by", "rules"),
)
```

**Proposed change:** Use Python's dataclass field names directly via `**d` with only the required coercions applied:

```python
@app.post("/api/chip")
def api_chip(req: SpecRequest):
    from app.pipeline import run
    try:
        d = req.spec
        spec = QuerySpec(
            aoi_name=d["aoi_name"],
            bbox=list(d["bbox"]),
            start=d["start"],
            end=d["end"],
            product=d.get("product", "true_color"),
            max_aoi_cloud=float(d.get("max_aoi_cloud", 100.0)),
            source_text=d.get("source_text", ""),
            parsed_by=d.get("parsed_by", "rules"),
        )
```

The minimal fix is making `SpecRequest` use a typed Pydantic model matching `QuerySpec` so that field validation happens at the request layer, not in the endpoint body. Replace `SpecRequest`:

```python
from pydantic import BaseModel
from typing import Literal, List

class QuerySpecRequest(BaseModel):
    aoi_name: str
    bbox: List[float]
    start: str
    end: str
    product: Literal["true_color", "ndvi", "ndwi"] = "true_color"
    max_aoi_cloud: float = 100.0
    source_text: str = ""
    parsed_by: Literal["rules", "llm"] = "rules"

class SpecRequest(BaseModel):
    spec: QuerySpecRequest

@app.post("/api/chip")
def api_chip(req: SpecRequest):
    from app.pipeline import run
    try:
        s = req.spec
        spec = QuerySpec(
            aoi_name=s.aoi_name,
            bbox=s.bbox,
            start=s.start,
            end=s.end,
            product=s.product,
            max_aoi_cloud=s.max_aoi_cloud,
            source_text=s.source_text,
            parsed_by=s.parsed_by,
        )
        result = run(spec)
        return _dc_to_dict(result)
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))
```

Pydantic now validates types at the boundary. A missing required field returns HTTP 422 with a descriptive error instead of a Python `KeyError` wrapped in a 500.

## 8. Cache Key Doesn't Include `max_aoi_cloud`

**Problem:** [`app/pipeline.py:114`](app/pipeline.py:114) builds the cache key as:
```python
cache_key = f"{spec.aoi_name}_{_bbox_hash(spec.bbox)}_{spec.product}_{spec.start}_{spec.end}"
```
`max_aoi_cloud` is not part of the key. A user who runs the same query twice — once with "only clear days" (max=10) and once without — gets the cached result from the first run on the second query. The cached result may contain candidates that exceed the new threshold.

**Current code:** [`app/pipeline.py:114`](app/pipeline.py:114)

**Proposed change:** Include `max_aoi_cloud` in the cache key:
```python
cache_key = (
    f"{spec.aoi_name}_{_bbox_hash(spec.bbox)}_{spec.product}"
    f"_{spec.start}_{spec.end}_{spec.max_aoi_cloud}"
)
```

One line change, no logic change.

## 9. `parse_rules` Falls Through to a Global Bbox Silently

**Problem:** When no AOI name is found and no `bbox=` literal is present, [`app/parse.py:123-125`](app/parse.py:123) sets:
```python
aoi_name = "unknown"
bbox = [-180, -90, 180, 90]
```
A global bbox sent to STAC will timeout or return nonsensical data. The user sees either a very slow response or a confusing server error. There's no inline feedback to the UI explaining that the AOI wasn't understood.

**Current code:** [`app/parse.py:123-125`](app/parse.py:123)

**Proposed change:** The `QuerySpec` is still returned (rules should never raise), but the `aoi_name` should carry a signal the UI can act on. Set it to a sentinel and let the UI check before even calling `/api/chip`:

In `parse_rules`:
```python
if aoi_name is None:
    aoi_name = "__unknown__"
    bbox = [-180, -90, 180, 90]
```

In `/api/parse` response, the UI can check:
```js
// After /api/parse returns spec:
if (spec.aoi_name === "__unknown__") {
  setStatus(`<div class="error-box">
    Couldn't find an AOI in your query. Try one of the example queries,
    or add a location name like "willamette", "punjab", or a
    <code>bbox=[w,s,e,n]</code> literal.
  </div>`);
  btn.disabled = false;
  return;
}
```

This stops the pipeline call entirely and gives an actionable error. No change to backend logic beyond the sentinel string.

## 10. Image Cards Have No Click-to-Enlarge

**Problem:** The three image cards render at one-third of the content column width (~330 px). Sentinel-2 chips at 10 m resolution over an 8 km × 8 km AOI contain a lot of detail that is invisible at this size. There is no way to see a larger version without opening DevTools and extracting the `src` URL.

**Current code:** [`web/index.html:99-108`](web/index.html:99)
```css
.img-card img { width: 100%; display: block; }
```

**Proposed change:** Wrap each image in an `<a>` that opens the full-resolution PNG in a new tab:

```js
card.innerHTML = `
  <a href="${url}" target="_blank" rel="noopener" title="Open full resolution">
    <img src="${url}" loading="lazy" style="display:block;width:100%" />
  </a>
  <div class="img-label">${label}</div>
`;
```

One line per card. No CSS changes, no API changes. The `target="_blank"` opens the `/outputs/…` URL which is already served by the `StaticFiles` mount.
